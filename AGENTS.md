# TXST Lynx — project foundation

**What this file is.** Everything an outsider needs to be useful on this project
in one place. It is written for AI assistants — ChatGPT, Claude, Copilot, Cursor,
Gemini — and for any human joining mid-semester. `AGENTS.md` is the filename
several of those tools look for automatically; if yours does not, paste this
whole file into the conversation before asking it anything about the project.

**What this file is not.** Setup instructions. Those are in `README.md` and are
good — how to install, run the frontend and backend, configure `.env`, and use
the migration workflow. This file covers what the README does not: what the
product actually is, which rules are settled, and which mistakes an assistant
reliably makes when it guesses.

**Keep it current.** If you change a product rule, a decision, or the data model,
change it here in the same commit. A stale context file is worse than none,
because it is believed.

## 1. What we are building

TXST Lynx is a social platform for Texas State University students, for a
semester-long software engineering course (CS 4398, September–December 2026).
Sign-up is restricted to `txstate.edu` addresses.

It is forum-shaped rather than timeline-shaped. Content lives in **spaces**, and
there are three kinds:

- **General** — one campus-wide space for anything that belongs to the whole
  university.
- **Colleges** — a fixed, seeded set. Students do not create these. A student
  declares one home college.
- **Communities** — created and run by students, for a club, a course, a dorm,
  an interest.

A student posts into exactly one space. Others like it and reply in threaded
comments. Likes plus age produce a ranking, and each space has Hot, New and Top
orderings. A student follows spaces to assemble a personal feed.

Every post is screened by a machine-learning classifier **before** anyone but
its author can see it. Comments are not screened and publish immediately.
Students can report content and accounts that the classifier missed.

## 2. Rules that are already settled

These are decided. Do not propose alternatives unless explicitly asked to
revisit one — several were argued through and closed deliberately.

| Rule | Detail |
|---|---|
| **Upvotes only** | There is no downvote anywhere in this product. A like is the existence of a row. There is no `value` column holding `+1/-1`, and no score arithmetic. |
| **General is a place** | It is a destination you post *to*, not an aggregate view of the other spaces. A post appears in exactly one feed. |
| **Nobody follows a person** | The social graph connects people to spaces only. No user-to-user following, no friend requests. |
| **One `spaces` table** | Campus, colleges and communities are one table with a `kind` enum, not three parallel tables. This is decision `[D-2]` and reversing it costs six tables and every feed query. |
| **Supabase Auth owns identity** | We store no passwords. `public.profiles.id` **is** `auth.users.id`. |
| **`txstate.edu` only** | Enforced in the database by a trigger on `auth.users`, not only in application code. |
| **Screening precedes publication** | A post exists as `pending` and is invisible to everyone but its author until the classifier approves it. Comments are not screened; they are created `approved`. |
| **ForAll moderation is automatic** | By default, any overall/category flag blocks publication. An experimental backend-only local opt-in can recheck lower-score text `violence`, alone or paired with `harassment`, for a confirmed past-incident or ordinary animal context; it is off by default. Screening failures stay pending with bounded retries; no human-review dependency at this feed level (FR-90–92). |
| **Colleges are seeded** | Ten of them, inserted by migration. Users cannot create a college. |

## 4. The data model

Eighteen tables of ours, plus Supabase's `auth.users` which we do not own.

**Identity**
- `profiles` — a student. `id` is `auth.users.id`. Holds username, bio, a
  normalized major selection, optional academic level, home college, avatar and
  banner upload references, karma totals, admin flag, and suspension. `email` and
  `email_verified_at` are **mirrored from `auth.users` by trigger** — never
  write them from application code.
- `majors` — active TXST undergraduate catalog choices, including degree
  variants. Each belongs to one college so profile forms can filter and validate
  choices. They are profile metadata, not spaces, and do not resolve `[D-5]`.
- `colleges` — one row per college space: crest, accent colour, sort order.

**Places**
- `spaces` — General, colleges and communities, discriminated by `kind`.
- `follows` — `(user_id, space_id)` plus `muted`. Composite PK, so following
  twice is impossible rather than merely handled.
- `moderators` — `(space_id, user_id)`. Deliberately separate from `follows`;
  moderating is not a stronger kind of following.
- `bans` — `(space_id, user_id)` with an optional expiry.

**Content**
- `posts` — one `space_id`, required title, and one `type` (`text` / `link` /
  `image`). Text requires a body; images may also have text; legacy links use
  `url`. `submission_id` makes post-create retries idempotent per author.
  Moderation attempt counts, retry time, claim/lease and exhaustion fields make
  committed pending rows a durable queue for the ForAll worker.
- `post_media` — ordered `(post_id, position)` attachments referencing completed
  `image_uploads`, with object key and dimensions. A deferred database constraint
  requires media for image posts and forbids it for text/link posts. Nullable
  upload references/dimensions preserve legacy image keys.
- `comments` — threaded. `path` is an `ltree` holding the ancestry, so a whole
  thread loads in one indexed query with no recursion. `parent_id` is kept
  alongside it on purpose and the two must be written in the same statement.
- `image_uploads` — an owner, private Storage object key, file name, MIME type,
  byte size, browser-measured width/height, and upload timestamps. Independent
  of posts so the upload pipeline can be tested and reused before post creation.
  `uploaded_at` means transfer confirmed, **not moderation approved**. Source
  dimensions are browser-reported. A trusted worker independently decodes still
  images and generates purpose-specific WebP versions; see `docs/image-processing.md`.
- `image_variants` — immutable optimized versions per upload: post preview/expanded,
  avatar small/large, or one banner; measured size and dimensions, private object keys.
- `image_processing_checks` — asset-level screening audit, separate from post audits.
  Uploads carry durable processing claims, retries, original cleanup state and
  reference-aware asset retirement/deletion state.
- `image_storage_objects` — owner-scoped file/capacity ledger. Object rows retain
  confirmed deletion timestamps and orphan retry state; historical metadata costs
  no image storage.

**Engagement**
- `post_likes`, `comment_likes` — composite PK `(user_id, target_id)`. Unliking
  is a `DELETE`.

**Safety**
- `moderation_checks` — label, score, decision, model, latency, full category
  results, policy version, content hash and attempt number. Written atomically
  with the publication decision; contains no signed image URLs or credentials.
- `reports` — what a person said. Targets exactly one of a post, a comment, or
  an account. Content reports go to that space's moderators; account reports go
  to site administrators, enforced by a CHECK constraint.

**Conventions throughout:** UUID primary keys; `timestamptz` everywhere, never
`timestamp`; soft delete via `deleted_at` with partial indexes that exclude
tombstones; counter columns (`like_count`, `follower_count`, karma) are caches
that must be written in the same transaction as the row they summarise.

## 5. Architectural rules

1. **The frontend never queries the database for application data.** It calls
   FastAPI, which answers in JSON. (One caveat — see §8.)
2. **Schema changes are migrations, committed to git.** Never change the shared
   database by clicking in the Supabase dashboard. `supabase migration new`,
   then `supabase db push`.
3. **`backend/models.py` mirrors the migrations by hand.** There is no
   autogeneration. Change one, change the other in the same commit.
4. **Requirements are numbered `FR-01` … `FR-99`** and the list lives at the top
   of `20260910200000_lynx_core.sql`. Cite them in commits, tests and status
   updates. The numbers are stable — never renumber, never reuse a retired one.
5. **Rules live in the database where they can.** `txstate.edu`, one-like-per-
   person, one-body-type-per-post, one-campus-space, report routing: all
   constraints, so violating them is impossible rather than discouraged.
6. **Row Level Security is on for every table.** A Supabase table with RLS on and
   no policy returns zero rows to the API — which looks exactly like a broken
   query. If a query mysteriously returns nothing, suspect RLS first.
7. **Rankings are computed on write, never on read.** `hot_rank` is a stored
   column: `log(greatest(like_count,1)) + extract(epoch from created_at)/45000`.
8. **Images never enter the database.** Store object keys; upload directly
   from browser to Storage using the student’s Auth session and an open reservation. Trusted background workers may
   read image bytes for validation, optimization and screening; API requests
   continue to carry metadata.

## 6. Open decisions

Marked `[D-n]` in the migration at the exact place they bite. **Do not silently
pick one** — if a question depends on an open decision, say so.

| ID | Question | Status |
|---|---|---|
| `[D-1]` | Who owns authentication? | **Closed** — Supabase Auth. |
| `[D-2]` | One `spaces` table or three? | **Closed** — one, with a `kind`. |
| `[D-3]` | Comment tree as a materialised `ltree` path | Implemented, not yet reviewed by the team. |
| `[D-4]` | What happens when the classifier does not answer? | **Resolved for new ForAll posts:** remain pending; default 3 total background attempts, with 30s/120s retry delays. Exhausted posts remain private and show a failure notice. Settings are configurable; editing remains future work; owner-requested screening retries are implemented below. See `docs/moderation.md`. |
| `[D-5]` | Colleges or departments? | **Open.** The seed holds the ten real colleges, so computer science shares a bucket with biology and maths. Per-department would be ~40–50 spaces. One `INSERT` to change; large effect on how the product feels. |

## 7. Where the project is

Sprint 1 (Sept 1–13) — foundation — is essentially complete: both apps run,
they talk to each other, Postgres is connected through SQLAlchemy, migrations
are version-controlled, and the full schema is merged into `dev`.

Working endpoints today are `GET /health`, `GET /db-health`, `GET /profiles`,
`GET /auth/me`, `PATCH /auth/me`, and `GET /profile/options`. `/login` signs
existing users in through Supabase Auth.
FastAPI validates bearer tokens with the project's Auth server, then loads the
matching profile. Inactive accounts are rejected (FR-96); a reusable write
dependency requires verified email (FR-02). Post routes derive `author_id` from
that profile and check bans for the target space (FR-95).
Application queries still use the server's SQLAlchemy connection, not the
browser's Supabase client. Auth does not automatically apply viewer RLS to SQL.
General posts, ordered images, chronological feed reads and post likes work
through `/posts`. Threaded comments, replies, comment likes and deletion are also
implemented. Reports remain **schema only**.
When explicitly enabled, the FastAPI lifespan starts a ForAll moderation worker
(FR-90–92), selecting
eligible pending posts oldest first, including the backlog. OpenAI screens
title/body plus attached images; by default any flag blocks, otherwise the post
is approved. Each image uses a separate request with the title/body. All images
must pass for approval; the first flag blocks the whole post, while a request
failure before a blocking verdict leaves it pending for retry. The JSON audit
retains each checked image's position and result without signed URLs (FR-90–92).
The local, disabled-by-default `MODERATION_CONTEXT_RECHECK_ENABLED`
option can let a second model clear a lone lower-score text `violence` flag, or
the combination of `violence` and `harassment` when it identifies a past
incident or ordinary animal context and both scores are below the experimental
ceilings.
Claims and retry counts persist across restarts; stale results cannot publish.
Audits and verdicts commit together. Pending cards refresh via `GET /posts/{id}`
and show exhausted failures. There is no human review or account suspension in
this slice. Report-handling rules are saved for later work (FR-97–99).
An offline contextual evaluation compares the default any-flag rule with this
candidate on synthetic text cases; the optional worker path is for local tests
only pending representative, independently labeled evaluation.
Results and limitations are in `docs/moderation.md`.

running this checkout. The latter is not deployed to the shared database.

worker decodes still images (25 million pixel cap), strips metadata, generates

Post assets produce preview + expanded versions; avatars produce small + large;

Shared image state and retry eligibility live in `backend/images/lifecycle.py`.
Posts wait for image processing without consuming post-screening attempts, then

send bounded inline image

`/upload-test` is a Next.js page for the reusable image upload pipeline (FR-32).

Implemented slice: persistent General/ForAll posts with required titles,

## 8. Things assistants get wrong here

Ranked by how often a fresh model guesses wrong. Every item below has a specific
correct answer.

1. **The user table is `profiles`, not `users`.** `users` exists but it is
   `auth.users`, owned by Supabase, and we do not write to it. Code referring to
   a `users` table is wrong.
2. **There are no downvotes.** Suggesting a `value` column, a `votes` table, or
   score arithmetic contradicts a settled decision. A like is a row.
3. **General is not an aggregate feed.** It does not blend the other spaces. It
   is one row in `spaces` with `kind = 'campus'`.
4. **Colleges, communities and General are one table.** Do not propose a
   `communities` table; `[D-2]` closed this.
5. **Users cannot follow users.** `follows` points at spaces only.
6. **We store no passwords.** No `password_hash`, no bcrypt, no session table.
   Supabase Auth handles login, sessions and the verification email.
7. **`profiles.email` is trigger-maintained.** Application code writing it is a
   bug. Same for `email_verified_at`.
8. **A `pending` post is not a draft.** It is submitted and awaiting the
   classifier. Its author sees it; nobody else does.
9. **Do not suggest editing the database directly.** Every change is a migration
   file in `supabase/migrations/`.
10. **`comments.path` is not decoration.** It is how threads are read. Writing a
    comment without setting `path` and `parent_id` together breaks the tree.

`image_uploads.recovery_required` protects completed inputs after infrastructure
failures, including retries exhausted or interrupted. They remain charged once
until confirmed deletion. They are excluded from automatic unused-asset retirement
and original cleanup; pending profile references remain available for recovery.
Storage has a BEFORE DELETE guard for originals, including service-role requests:
only complete confirmed variant sets, invalid/expired inputs, or explicitly
retired/abandoned assets may lose the source. Bounded retries remain; recovery
retention has no automatic expiry. Owners can deliberately discard unused assets
with `DELETE /images/{id}` after active references are removed.

A credential failure pauses BOTH workers in that backend process. It preserves
the current input and refunds its credential-failed attempt, then claims no more
jobs or cleanup. Fix configuration and restart to resume; other machines are not
controlled by this process. `GET /workers/status` requires sign-in and reports
that process's worker ID, enabled flags and pause reason. Use one designated
backend for shared testing. Logs contain worker/job IDs and safe error codes,
never image data, provider bodies or credentials.

Owners can use `POST /images/{id}/retry` and `POST /posts/{id}/retry-screening`
(or the profile/feed/upload-test controls). Retries reuse the same asset and input,
check source accounting, unfinished slots and available processing headroom under
the account lock, and cannot approve/retry rejected content. Concurrent retries
are idempotent; no new original reservation or upload-rate charge is created.
Preserved inputs and uncertain files continue to consume storage. A missing or
already-deleted source requires re-upload. There is no way to recover removed
Storage bytes merely by resetting database metadata.
