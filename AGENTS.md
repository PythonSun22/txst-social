# Boko Lynx — project foundation

**What this file is.** Everything an outsider needs to be useful on this project
in one place. It is written for AI assistants — ChatGPT, Claude, Copilot, Cursor,
Gemini — and for any human joining mid-semester. `AGENTS.md` is the filename
several of those tools look for automatically; if yours does not, paste this
whole file into the conversation before asking it anything about the project.

**What this file is not.** Setup instructions. Those are in `README.md` and are
good — how to install, run the frontend and backend, configure `.env`, and use
the migration workflow. This file covers what the README does not: what the
product actually is, which rules are settled, and which mistakes an assistant
reliably makes when it guesses.

**Keep it current.** If you change a product rule, a decision, or the data model,
change it here in the same commit. A stale context file is worse than none,
because it is believed.

## 1. What we are building

Boko Lynx is a social platform for Texas State University students, for a
semester-long software engineering course (CS 4398, September–December 2026).
Sign-up is restricted to `txstate.edu` addresses.

It is forum-shaped rather than timeline-shaped. Content lives in **spaces**, and
there are three kinds:

- **General** — one campus-wide space for anything that belongs to the whole
  university.
- **Colleges** — a fixed, seeded set. Students do not create these. A student
  declares one home college.
- **Communities** — created and run by students, for a club, a course, a dorm,
  an interest.

A student posts into exactly one space. Others like it and reply in threaded
comments. Likes plus age produce a ranking, and each space has Hot, New and Top
orderings. A student follows spaces to assemble a personal feed.

Every post and comment is screened by a machine-learning classifier **before**
anyone but its author can see it, and students can report content and accounts
that the classifier missed.

## 2. Rules that are already settled

These are decided. Do not propose alternatives unless explicitly asked to
revisit one — several were argued through and closed deliberately.

| Rule | Detail |
|---|---|
| **Upvotes only** | There is no downvote anywhere in this product. A like is the existence of a row. There is no `value` column holding `+1/-1`, and no score arithmetic. |
| **General is a place** | It is a destination you post *to*, not an aggregate view of the other spaces. A post appears in exactly one feed. |
| **Nobody follows a person** | The social graph connects people to spaces only. No user-to-user following, no friend requests. |
| **One `spaces` table** | Campus, colleges and communities are one table with a `kind` enum, not three parallel tables. This is decision `[D-2]` and reversing it costs six tables and every feed query. |
| **Supabase Auth owns identity** | We store no passwords. `public.profiles.id` **is** `auth.users.id`. |
| **`txstate.edu` only** | Enforced in the database by a trigger on `auth.users`, not only in application code. |
| **Screening precedes publication** | A post exists as `pending` and is invisible to everyone but its author until the classifier approves it. |
| **Colleges are seeded** | Ten of them, inserted by migration. Users cannot create a college. |

## 4. The data model

Twelve tables of ours, plus Supabase's `auth.users` which we do not own.

**Identity**
- `profiles` — a student. `id` is `auth.users.id`. Holds username, bio, major,
  home college, karma totals, admin flag, suspension. `email` and
  `email_verified_at` are **mirrored from `auth.users` by trigger** — never
  write them from application code.
- `colleges` — one row per college space: crest, accent colour, sort order.

**Places**
- `spaces` — General, colleges and communities, discriminated by `kind`.
- `follows` — `(user_id, space_id)` plus `muted`. Composite PK, so following
  twice is impossible rather than merely handled.
- `moderators` — `(space_id, user_id)`. Deliberately separate from `follows`;
  moderating is not a stronger kind of following.
- `bans` — `(space_id, user_id)` with an optional expiry.

**Content**
- `posts` — one `space_id`, one `type` (`text` / `link` / `image`), and exactly
  one of `body` / `url` / `image_key`, enforced by CHECK constraint.
- `comments` — threaded. `path` is an `ltree` holding the ancestry, so a whole
  thread loads in one indexed query with no recursion. `parent_id` is kept
  alongside it on purpose and the two must be written in the same statement.

**Engagement**
- `post_likes`, `comment_likes` — composite PK `(user_id, target_id)`. Unliking
  is a `DELETE`.

**Safety**
- `moderation_checks` — what the model said: label, score, decision, model
  version, latency. Kept so thresholds can be tuned and false positives audited.
- `reports` — what a person said. Targets exactly one of a post, a comment, or
  an account. Content reports go to that space's moderators; account reports go
  to site administrators, enforced by a CHECK constraint.

**Conventions throughout:** UUID primary keys; `timestamptz` everywhere, never
`timestamp`; soft delete via `deleted_at` with partial indexes that exclude
tombstones; counter columns (`like_count`, `follower_count`, karma) are caches
that must be written in the same transaction as the row they summarise.

## 5. Architectural rules

1. **The frontend never queries the database for application data.** It calls
   FastAPI, which answers in JSON. (One caveat — see §8.)
2. **Schema changes are migrations, committed to git.** Never change the shared
   database by clicking in the Supabase dashboard. `supabase migration new`,
   then `supabase db push`.
3. **`backend/models.py` mirrors the migrations by hand.** There is no
   autogeneration. Change one, change the other in the same commit.
4. **Requirements are numbered `FR-01` … `FR-99`** and the list lives at the top
   of `20260910200000_lynx_core.sql`. Cite them in commits, tests and status
   updates. The numbers are stable — never renumber, never reuse a retired one.
5. **Rules live in the database where they can.** `txstate.edu`, one-like-per-
   person, one-body-type-per-post, one-campus-space, report routing: all
   constraints, so violating them is impossible rather than discouraged.
6. **Row Level Security is on for every table.** A Supabase table with RLS on and
   no policy returns zero rows to the API — which looks exactly like a broken
   query. If a query mysteriously returns nothing, suspect RLS first.
7. **Rankings are computed on write, never on read.** `hot_rank` is a stored
   column: `log(greatest(like_count,1)) + extract(epoch from created_at)/45000`.
8. **Images never enter the database.** Store the object key; upload directly
   from browser to storage with a signed URL.

## 6. Open decisions

Marked `[D-n]` in the migration at the exact place they bite. **Do not silently
pick one** — if a question depends on an open decision, say so.

| ID | Question | Status |
|---|---|---|
| `[D-1]` | Who owns authentication? | **Closed** — Supabase Auth. |
| `[D-2]` | One `spaces` table or three? | **Closed** — one, with a `kind`. |
| `[D-3]` | Comment tree as a materialised `ltree` path | Implemented, not yet reviewed by the team. |
| `[D-4]` | What happens when the classifier does not answer? | **Open.** Fail closed, fail open, or bounded wait. Bounded wait (~2s, then `pending`, retry in background) is recommended but not agreed. Editing raises the same question — an edited body has not been screened. |
| `[D-5]` | Colleges or departments? | **Open.** The seed holds the ten real colleges, so computer science shares a bucket with biology and maths. Per-department would be ~40–50 spaces. One `INSERT` to change; large effect on how the product feels. |

## 7. Where the project is

Sprint 1 (Sept 1–13) — foundation — is essentially complete: both apps run,
they talk to each other, Postgres is connected through SQLAlchemy, migrations
are version-controlled, and the full schema is merged into `dev`.

Working endpoints today are `GET /health`, `GET /db-health` and `GET /profiles`.
That is all. Posts, comments, likes, feeds, auth and moderation are **schema
only** — the tables exist, the API does not.

Sprint 2 (Sept 14–27) is the first vertical slice: posts through every layer,
create and retrieve, browser to database and back.

**Branches:** `main` is stable, `dev` is where work integrates, feature branches
come off `dev` and go back via pull request. Do not work on `main`.

## 8. Things assistants get wrong here

Ranked by how often a fresh model guesses wrong. Every item below has a specific
correct answer.

1. **The user table is `profiles`, not `users`.** `users` exists but it is
   `auth.users`, owned by Supabase, and we do not write to it. Code referring to
   a `users` table is wrong.
2. **There are no downvotes.** Suggesting a `value` column, a `votes` table, or
   score arithmetic contradicts a settled decision. A like is a row.
3. **General is not an aggregate feed.** It does not blend the other spaces. It
   is one row in `spaces` with `kind = 'campus'`.
4. **Colleges, communities and General are one table.** Do not propose a
   `communities` table; `[D-2]` closed this.
5. **Users cannot follow users.** `follows` points at spaces only.
6. **We store no passwords.** No `password_hash`, no bcrypt, no session table.
   Supabase Auth handles login, sessions and the verification email.
7. **`profiles.email` is trigger-maintained.** Application code writing it is a
   bug. Same for `email_verified_at`.
8. **A `pending` post is not a draft.** It is submitted and awaiting the
   classifier. Its author sees it; nobody else does.
9. **Do not suggest editing the database directly.** Every change is a migration
   file in `supabase/migrations/`.
10. **`comments.path` is not decoration.** It is how threads are read. Writing a
    comment without setting `path` and `parent_id` together breaks the tree.

## 9. Known inconsistencies

Real, unresolved, and worth knowing before you trust any single document.

**The project has three names.** `README.md` and the first migration say
**TXST Lynx**. The proposal and the core migration say **Boko Lynx**. The
documentation standard and the sprint timeline say **TXST Social**. The GitHub
repository is `txst-social`. Nothing is broken by this, but it should be settled
and applied everywhere — pick one and do a pass.

**Direct database access from the browser is ambiguous.** `README.md` says all
application database access goes through FastAPI. The RLS policies in
`20260910200000_lynx_core.sql` deliberately permit a signed-in browser to insert
and delete its own likes and follows directly, on the reasoning that those need
no decision, while anything requiring one — screening, rate limits, moderator
scope — must go through the API. **Both are defensible; only one can be the
rule.** The team has not chosen. Until it does, prefer routing through FastAPI,
which is the more conservative reading and matches what is written down.
