Start here — the boundary

The one thing to understand before reading the diagram: we do not store passwords.

Supabase Auth owns credentials, sessions, password resets and the verification email. It keeps those in its own table, auth.users, drawn in gold and dashed below because it sits outside our schema. Our profiles row uses the very same id, so the foreign key between them is the seam between what Supabase owns and what the application owns.

Two values are copied across that seam by a database trigger — a student's address and whether they have confirmed it. That copy exists for two concrete reasons: FR-01 limits the product to txstate.edu, and a CHECK constraint cannot see into another table; and FR-02 gates every post, comment and like on being verified, which would otherwise mean a cross-schema join on every single write.

Entity relationships

What each group is for

Identity

  • profiles A student. Keyed to Supabase Auth; owns the karma totals and the admin flag.
  • colleges The crest, accent colour and sort order — the bits only a college has.

Places

  • spaces General, a college, or a student-made community. One table, one kind.
  • follows Who follows what, and whether they've muted it.
  • moderators Who may remove things, and only inside their own space.
  • bans Who may not post there, and until when.

Content

  • posts Text, link or image — exactly one of the three, enforced by the database.
  • comments The thread. path stores the ancestry so a whole tree loads in one query.

Engagement

  • post_likes A like is the row. No +1/-1 column, because there are no downvotes.
  • comment_likes Same shape. Unliking is a delete; liking twice is impossible.

Safety

  • moderation_checks What the classifier thought, kept so thresholds can be tuned later.
  • reports What a person thought. A report on content the model passed is a labelled miss.

Three decisions still open

D-4

What happens when the classifier doesn't answer?

FR-90 puts a model call between “pressed Post” and “post exists”. That call can be slow, time out, or return 503 because the service is asleep. The schema supports all three answers; the difference is invisible in code review and obvious in a demo.

  • Fail closed — nothing unscreened is ever published, but if the model is down during the presentation, posts silently stop appearing and the app looks broken.
  • Fail open — always fast, always works, but content is readable before it has been checked, which is the one thing FR-90 exists to prevent.
  • Bounded wait — wait about two seconds, then fall back to pending and retry in the background. The common case stays fast and the failure case is safe rather than merely quiet. Recommended.

Editing raises the same question again: an edited body has not been screened. Re-screen on edit, or the checker is bypassed by posting something clean and editing it afterwards.

D-5

Colleges, or departments?

The seed currently holds the ten real Texas State colleges, so a computer science student lands in one bucket with biology, maths and engineering. A per-department list would give CS its own feed — closer to what was described — at roughly forty to fifty spaces. It is a change to one INSERT and nothing else structurally, but it changes how the product feels, so it wants deciding before the demo rather than after.

D-3

Comment trees as a materialised path

Implemented, not yet reviewed. path holds the ancestry as an ltree — 0001.0004.0009 — so a whole thread loads correctly sorted in one indexed query with no recursion. parent_id is kept alongside it on purpose: the path makes reads fast, the parent keeps referential integrity real. The redundancy is deliberate, and the two must always be written in the same statement. The team should be comfortable maintaining that before it ships.

It caught one real bug

The trigger functions set search_path = '', which is correct and required for a security definer function. That also made the unqualified citext type unresolvable inside them — so every signup would have failed at runtime. The file parsed perfectly. It would have died in front of the class. Fixed by comparing as text and letting the implicit cast do the rest.
